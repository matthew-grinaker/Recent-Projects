A delivery harness where agents build and plain code keeps them honest.

Since 2025 I've built the system I use to run software delivery through AI agents. One agent coordinates, workers build, and an independent reviewer grades every ticket. The harness

From PRD to merged code

The flow of one run. I sign off at the steps marked in white; every other step runs unattended, inside hard limits.

  1. PlanThe PRD optimiser turns an idea or SOW into PRDs. I approve them.
  2. CoordinateThe coordinator orders tickets by dependency and writes a prompt per ticket. I say go.
  3. BuildHeadless workers, one per ticket, each in its own branch, with hooks on every step. Anything unclear comes back to me.
  4. ReviewA fresh grader with no shared context reruns the checks. Fails go back with evidence.
  5. IntegratePassed tickets merge into an integration branch. A goal audit turns gaps into new tickets.
  6. ShipI review and merge to main. CI reruns the tests and accuracy baselines, and main deploys to staging. I deploy to production by hand. Agents can't reach staging or production. Every ticket keeps its log, cost and verdict.

    Separation of roles

    Coordinator, worker, reviewer

    No agent checks its own work, and no worker can change what it's judged against.

    Coordinator

    Plans, gates and judges. Never implements.

    • Turns PRDs into tickets ordered by dependency.
    • Sets each worker's model, effort, budget and turn cap.
    • Writes and owns the tests. Workers can read them but never change them, because workers were caught editing tests so they would pass.
    • Is the only one that merges, and only into an integration branch.
    Worker

    One headless Claude Code session per ticket.

    • Works in its own branch and worktree, so parallel tickets never collide.
    • Gets the PRD, the rulings it must follow and live repo state in its prompt.
    • Can't reach me directly. If something is unclear it stops and returns blocked with a reason, and that comes back to me.
    Reviewer

    A fresh reviewer every round, with no shared context.

    • Reruns the checks itself instead of trusting the worker's report.
    • Returns a structured JSON verdict, never text to grep.
    • Passes a ticket only when every check runs clean and every acceptance criterion is met. A separate validator agent scores 7 weighted criteria from 0 to 100, passing at 85, with 10 hard gates.

    Evals, memory, communication

    What keeps the agents on track

    Evals and quality gates

    Every result is checked by code, never by the agent that made it.

    • Grader gateNothing merges without a pass from the grader.
    • Goal auditAfter each run, gaps become new tickets, for up to 3 rounds. The same gap twice stops the run.
    • Accuracy baselinesEach document type has one, and CI fails if it drops.
    • Claude PulseTurns every verdict into a score worked out by code from weighted criteria. A failed must-have fails the run, however good the average.

    Agent‑to‑agent communication

    Structured handoffs between agents, sessions and tools.

    • Files and exit codesThe coordinator and workers swap a prompt in for a JSON outcome out.
    • Message busIn GTech OS, agents pass work over a replayable message bus.
    • Second brainShared across sessions: decisions, handovers and time-limited work claims.
    • FleetSessions on my machine can list, read and message each other. A message is held back while the other session has a question open.
    • Shared inboxClaude Code and Codex share the same agents and a local inbox for handoffs.

    Memory in Obsidian

    Run history and code knowledge live in one vault, so each session starts from what earlier ones learned.

    • Claude Pulse notesOne note per agent session: score, verdict, criteria, team and roles, with a warning when it fails. Tags make every past run searchable.
    • RubricsVault notes written from each PRD's acceptance criteria, read back to score the next run.
    • graphifyMaps code and documents into a knowledge graph saved in the vault, so agents look things up instead of re-reading every file.
    • Context filesEvery repo carries one that agents read first, alongside CLAUDE.md, architecture rulings and the shared second brain.

    Decisions that improved output

    Problem, decision, result

    • Two agents undid each other's settled work.A decision log with supersession, plus work claims an agent must hold before it changes an area.Result: every session starts from the same picture.
    • Agents forgot architecture decisions after their context was compacted.A hook blocks an edit until the agent has read the relevant rulings.Result: settled decisions stay settled across long runs.
    • A worker could report success that hadn't happened.A grader with no shared context reruns the checks and returns a JSON verdict.Result: a pass means the checks passed, not that an agent said so.
    • A stuck session could run all weekend.Every worker has a cap on turns, spend and wall-clock time, and the whole run has a spend cap.Result: a stuck ticket hits its cap and fails, instead of running all weekend.
    • Prompts went stale as earlier tickets landed.Live branch, status and recent commits are injected when each session starts.Result: each worker sees the repo as it is now.
    • Workers were caught editing tests so they would pass.The coordinator writes and reviews the tests. Workers get read-only access to them.Result: a pass means the code met the test, not that the test was bent to fit.
    • A reviewer reused across loops skipped earlier tests it had already seen pass.A new reviewer starts every round and reruns the earlier tests too.Result: regressions from the next round of changes get caught.
    • Agents skipped steps without saying so.A checklist mod tracks every step of a run and flags the ones that were missed.Result: silent gaps become visible, along with which agents tend to skip steps.
    • An evaluator's score was a number you had to take on trust.Code adds up the score from weighted, named criteria, and a failed must-have fails the run outright.Result: a wrong call shows up against a named criterion, and must-haves can't be averaged away.
    • Agents spent their context re-reading the same code and documents.graphify builds a knowledge graph of the code and documents and saves it in the Obsidian vault.Result: agents look up what they need instead of reading everything again.
    • With many agents waiting, I answered whichever one I saw first.One inbox ranks every waiting question by how long it has waited and how many agents it holds up.Result: the answer that frees the most agent time comes first.
    • Autonomy that hadn't been earned.AI gets more responsibility only as evals show it can carry it.Result: I still approve every plan and every release to main.

    What this means for you

    Where it adds value

    Faster delivery, with control

    StockChain went live with its first customer in 7 months: about 2,700 commits and 1,100+ test files, mostly built through earlier versions of this pipeline, with me approving every plan and every release to main.

    Safe access to your systems

    Agents read live business data through read-only MCP servers (Odoo ERP, tenant-scoped PostgreSQL), get only the tools they need, a spend cap per run, and approvals that default to no.

    Visible and repeatable

    Every step is logged and replayable, cost is tracked per ticket and model, and clients get a plain-English progress report every week. The same PRD template and config run on any repo.

    Your work doesn't stall waiting on me

    Fleet gathers every question from agents on my Mac, in the cloud and in project threads into one inbox, ranked by how much agent time each one holds up, so the most costly wait gets answered first. I can answer from the Claude app, Slack or my phone, and Fleet can draft the likely answer for me to check. Agents spend less time idle, and your project keeps moving when I'm away from my desk.
